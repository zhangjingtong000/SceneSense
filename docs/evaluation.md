# 感知评估（Gate 0–2）

本目录实现验收 spec 要求的可执行评分链路，替代此前只有代理指标（drop_rate、id_switch）的做法。

## 口径

- **帧号**：统一使用视频 0 基帧号，`video_frame = mot_frame - 1`。
- **行人**：MOT17 真值中 `mark=1` 且 `class=1` 的行。
- **核心目标**：`visibility >= 0.5`、bbox 高 `>= 40px`、与画面交集 `>= 60%`。
  挑战目标单独统计，不计入硬门槛。
- **匹配**：同帧一对一，`IoU >= 0.5`，按 IoU 降序贪心。
- **指标**：
  - 人物发现率：某 GT 人物的核心帧中至少一次匹配。
  - 帧级召回/精确率：核心 GT 框与预测框的比值。
  - 连续漏检：只累计核心帧中连续未匹配的帧数（帧号不连续则断点）。
  - 错误合并：同一帧内不同 GT 人物匹配到同一 Entity 的次数。
  - 碎片数：每个已发现 GT 人物对应过的不同 Entity 数（平均）。

恢复率（Gate 2 的 95% / 80%）由 GT 的 `person_id` 在可见帧断口处**自动计算**
（`compute_recovery_rates`），不需要人工标注。只有两种情况返回 `None`：没传
`gt_by_frame` / `pred_by_frame`，或某一档（短/中/长间隔）没有可判定的「消失—重现」事件。
需要人工标注的只有 Gate 2 的连续性判定（`gate2_continuity`），那是另一件事。

## 命令

```bash
# 1. 导出逐帧预测（GPU 必需；CPU 回退会标记为配置错误）
python scripts/export_predictions.py --source test_data/mot17_180.mp4 \
    --model yolov8l.pt --device cuda --conf 0.15 --imgsz 1920 \
    --out outputs/pred/mot17_180.jsonl

# 2. 生成 Gate 报告（一条命令，含 Gate 0/1/2）
python scripts/run_gate.py --video test_data/mot17_180.mp4 \
    --predictions outputs/pred/mot17_180.jsonl --frame-count 180 \
    --out outputs/gate/mot17_180.json

# 或一步到位：先导出再评估
python scripts/run_gate.py --video test_data/mot17_180.mp4 --export \
    --model yolov8l.pt --device cuda --imgsz 1920 --frame-count 180 \
    --out outputs/gate/mot17_180.json

# 3. Gate 0 可重复性（连续 N 次核心指标必须一致）
python scripts/check_repeatability.py --video test_data/mot17_180.mp4 \
    --model yolov8l.pt --imgsz 1920 --runs 3 --max-frames 60
```

## 已知限制

- 未发现的两个 GT 人物（73、98）分别只出现在 0–8 帧与 164–179 帧，属视频首尾边缘个体。
- 最长连续漏检来自 GT 68/74/86（身高 164–190px 的大目标），集中在人群重叠区域，

## 遮挡恢复修复（2026-11-04）

**问题**：跨 3–4 秒遮挡后，同一人被赋予新实体（`Person-1` → `Person-2`）。

**根因**：`EntityProfileManager.max_position_gap_px` 默认 140 px。在 1280/1920 画面里，
人物几秒内的位移可达 500–900 px，重新出现的 track 被判为“位置不合理”，
因而无法合并回原实体，退化成新建实体。

**修复**：位置门限按画面宽度比例设置，`max_position_gap_px = max(140, 0.4 × 画面宽)`。
在 `pipeline.py`、`web/backend/pipeline_runner.py`、`scripts/export_predictions.py` 三处生效。

**验证**：

| 场景 | 结果 |
|---|---|
| M3Act 合成（1280×720），遮挡 4.28 s、73 帧完全不可见 | 恢复率 0% → **100%**（Person-1 → Person-1） |
| MOT17-04（1920×1080）180 帧 | 错误合并 0 → 0；召回/精确率/碎片数不变 |

说明：合成场景的遮挡真值来自 3D 投影，标注框比 YOLO 检测框偏大约 10–15%，
因此匹配阈值使用 0.35 而非 0.5；MOT17 路径仍使用 0.5。

## 遮挡恢复优化三步（2026-11-04）

评估口径：MOT17-04 完整 1050 帧，恢复率由 GT 的 `person_id` 在可见帧断口处自动计算，
按 0–2 s / 2–10 s / >10 s 分层，无需人工标注。

### 第一步：换行人 ReID 骨干

ImageNet ResNet18 → BoxMOT 的 OSNet（MSMT17 预训练，512 维）。

| 指标 | 改前 | 改后 |
|---|---|---|
| 短遮挡恢复 | 84.09% | **87.23%** |
| 中遮挡恢复 | 100%（6 例） | 63.64%（11 例） |
| 错误合并 | 50 | **3** |
| 平均碎片 | 1.426 | 1.621 |

过程中修复两个真实缺陷：

1. `EntityProfileManager._resolve_entity` 的候选集合是快照，合并后仍被遍历 → `KeyError`
   中断整段视频（1050 帧只产出 679 条记录，此前所有评估数据都是残缺的）。
2. 同一帧允许多个 track 占用同一实体（`_claimed_entities` 只记不查）→ 误合并的
   主要来源。加入 `_claimed_owner` 冲突检测后，误合并 185 → 3。

### 第二步：离线轨迹拼接（结论：不划算）

新增 `scripts/stitch_tracklets.py`，用「外观相似度 + 运动预测位置 + 时间间隔」拼接 tracklet。

| 阈值（外观/位置/间隔） | 拼接对 | 短遮挡恢复 | 错误合并 |
|---|---|---|---|
| 0.70 / 0.12 / 300 | 25 组 | 89.36% | 134 |
| 0.90 / 0.04 / 150 | 1 对 | 87.23% | 3 |
| 0.85 / 0.06 / 150 | 5 对 | 87.23% | 206 |

结论：MOT17 人群密集、衣着相似，外观不足以支撑可靠拼接。宽松阈值拼 5 对即引入
206 次误合并；严格阈值几乎拼不上。**恢复率最多 +2 pp，误合并代价不可接受**，
因此保留在线跟踪 + 实体融合，不启用离线拼接。

### 第三步：BoxMOT 标准基线对照

同一段视频、同一检测器（yolov8l / conf 0.15 / imgsz 1920），只替换关联器：

| 实现 | 短遮挡恢复 | 中遮挡恢复 | 错误合并 | 平均碎片 | 检测召回 |
|---|---|---|---|---|---|
| 本项目（OSNet + 实体融合） | 87.23% | **63.64%** | 3 | 1.621 | **91.82%** |
| BoxMOT BoT-SORT | **87.50%** | 37.50% | 0 | 1.610 | 86.43% |
| BoxMOT StrongSORT | 75.76% | 33.33% | 0 | 1.879 | 76.55% |

结论：

1. 自研关联器在短遮挡上已与 BoT-SORT 持平（87.23% vs 87.50%），中遮挡优于 BoT-SORT
   与 StrongSORT，检测召回也最高。
2. **spec 中 95% 的短遮挡恢复门槛在这个数据上不现实**——最好的公开实现也只有 87.5%。
   门槛应重新设定，或换用遮挡更温和的场景。
3. 离线轨迹拼接（AFLink 思路）在当前数据上无法带来净收益，与 StrongSORT 表现更低一致。

## 遮挡恢复继续优化（2026-11-05）

三步走完后短遮挡恢复停在 87.23%，逐条归因发现失败分两类：
`detection_miss`（重入后没检测到，多为评估口径问题）与 `new_track`（检测到但换了 ID）。

### 关键修复：lost 轨迹参与低分框匹配

原实现 Step 2（低分框二次匹配）只让 `confirmed` 轨迹参与，而**被遮挡后进入 `lost` 的轨迹被排除在外**——
遮挡后重新出现的人恰好只有低分框。修复后：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 检测召回 | 91.82% | **93.05%** |
| 短遮挡恢复 | 87.23% | **90.74%** |
| 中遮挡恢复 | 63.64% | **85.71%** |
| 错误合并 | 3 | 2 |
| 平均碎片 | 1.621 | 1.458 |

### 参数扫描（MOT17-04 完整 1050 帧）

| 配置 | 短遮挡恢复 | 中遮挡恢复 | 误合并 | 碎片 |
|---|---|---|---|---|
| match_thresh 0.65 / proximity 0.50 | 88.89% | 85.71% | 2 | 1.458 |
| match_thresh 0.55 / proximity 0.50 | 90.74% | 85.71% | 2 | 1.458 |
| **match_thresh 0.55 / proximity 0.35** | **92.73%** | 85.71% | 2 | 1.441 |
| match_thresh 0.55 / proximity 0.30 | 89.09% | 85.71% | 2 | 1.475 |
| match_thresh 0.45 / proximity 0.50 | 90.74% | 85.71% | 2 | 1.458 |
| lost_buffer 180 / 200（其余同基线） | 88.89% | 85.71% | 2 | 1.508 |

分辨率与置信度：

| 配置 | 短遮挡恢复 | 中遮挡恢复 | 误合并 | 碎片 | 速度 |
|---|---|---|---|---|---|
| **imgsz 1920 / conf 0.15（默认采用）** | **92.73%** | 85.71% | 2 | 1.441 | 2.87 fps |
| imgsz 2240 / conf 0.15（质量优先） | 92.31% | **100%** | **1** | **1.288** | 1.67 fps |
| imgsz 2560 / conf 0.15 | 91.23% | 86.67% | 2 | 1.484 | 1.44 fps |
| imgsz 1920 / conf 0.12 | 87.27% | 71.43% | 3 | 1.525 | — |

结论：`imgsz 2240` 在中遮挡、误合并、碎片上更好，但短遮挡略低且慢 1.7 倍；
`imgsz 2560` 与更低 `conf` 都不划算。
**默认配置：imgsz 1920 / conf 0.15 / match_thresh 0.55 / proximity_thresh 0.35；
对遮挡恢复要求更高的场景可切到 imgsz 2240。**

### 净收益

| 阶段 | 短遮挡恢复 | 中遮挡恢复 | 误合并 |
|---|---|---|---|
| 优化前 | 84.09% | 63.64% | 50（含缺陷） |
| 换 ReID + 修缺陷 | 87.23% | 63.64% | 3 |
| lost 参与低分框匹配 | 90.74% | 85.71% | 2 |
| **参数调优（最终）** | **92.73%** | **85.71%** | **2** |

对比同数据集 BoT-SORT（87.50% / 37.50%）与 StrongSORT（75.76% / 33.33%），
短遮挡高 5.2 pp，中遮挡高 22–48 pp。

剩余失败（79 个事件中 16 个）以 `detection_miss` 为主，其中多数是评估口径所致：
GT 是包含被遮挡部分的完整框，检测框只有可见部分，IoU 天然低于 0.5。

## 性能优化（2026-11-07）

原实现是完全串行的单线程循环：读帧 → 检测 → ReID → 跟踪，各阶段互相等待，
GPU 大部分时间空闲。实测端到端仅 2.2–3.1 fps。

### 关键改动：三段流水线

新增 `scripts/export_predictions_pipelined.py`：

- **读帧线程**：解码后放入队列（深度 8）
- **检测线程**：批量推理，可在主线程处理上一帧时提前处理后续帧
- **主线程**：只负责跟踪、实体融合与写文件

### 实测结果（MOT17-04 完整 1050 帧）

| 配置 | 速度 | 短遮挡恢复 | 召回 | 误合并 |
|---|---|---|---|---|
| 串行 + PyTorch | 2.2–3.1 fps | 92.73% | 93.13% | 4 |
| 流水线 + PyTorch | 7.53 fps | 92.73% | 93.13% | 4 |
| 流水线 + TensorRT | 8.81 fps | 92.45% | 92.72% | 1 |
| **流水线 + ReID 独立线程 + TensorRT** | **9.2–12.7 fps** | 92.45% | 92.72% | 1 |
| 流水线 + ReID 独立线程 + PyTorch | 10.5 fps | 92.73% | 93.13% | 4 |

**提升约 5 倍，精度无损。** TensorRT 引擎（`yolov8l.engine`，编译约 16 分钟）
只支持 batch=1；PyTorch 路径可用 batch=4。

ReID 独立线程的实现：检测线程完成一帧后立即把 ReID 任务提交到单线程池，
主线程消费该帧时特征通常已算好（`MultiObjectTracker.update` 新增 `features` 参数，
传入则跳过内部提取）。ReID 与检测在 GPU 上错峰执行，省下约 70 ms/帧。

### 试过但无效的方案

| 方案 | 结果 |
|---|---|
| 矩形 imgsz `(1088,1920)` 消除黑边 | 实测仅快 6%（子代理估算 40%，未成立） |
| batch=8/16 | 反而变慢（显存触顶降频） |
| YOLOv8m | 2.64 fps，精确率跌到 85.6% |
| imgsz 降到 1536/1280 | 召回从 93% 掉到 70–78% |
| ONNX Runtime | 与 PyTorch 的 CUDA 上下文冲突，报错 |

### 推荐用法

```bash
# 最快（需要先导出引擎）
python scripts/export_predictions_pipelined.py --source <video> \
    --model yolov8l.engine --imgsz 1920 --reid-interval 3 --batch-size 1 --out <jsonl>

# 不依赖 TensorRT
python scripts/export_predictions_pipelined.py --source <video> \
    --model yolov8l.pt --imgsz 1920 --reid-interval 3 --batch-size 4 --out <jsonl>
```

注意：同一配置在同机上速度会有 ±30% 波动（笔记本 GPU 温度/功耗节流），
评估结论应看精度指标，速度取多次的较优值。

## 多场景验证：单场景调参的过拟合（2026-11-07）

前文“遮挡恢复继续优化”中的提升全部在 MOT17-04 单场景上测得。为验证普适性，
在 **7 个 MOT17 场景 × 每场景 300 帧** 上做单变量拆分：

| 配置 | 平均短遮挡恢复 | 相对 base |
|---|---|---|
| **base（原逻辑 + 原阈值 0.65/0.50）** | **75.0%** | — |
| lost（仅让 lost 轨迹参与低分框匹配） | 69.1% | **−5.9 pp** |
| thr（仅改阈值到 0.55/0.35） | 73.2% | −2.8 pp |
| both（两项都开） | 69.1% | −5.9 pp |

结论：**两项“优化”在其他场景上均为负收益**，MOT17-04 上的 92.73% 是该场景的个例。

原因分析：低分框在密集场景里误检比例高，把 lost 轨迹与这些误检匹配会引入错误轨迹；
04 场景人少、检测质量高，所以该改动在那里有效。

**因此默认配置回退为原行为**（`include_lost_in_low_stage=False`，阈值 0.65/0.50）。
流水线与 ReID 独立线程带来的约 5 倍提速保持不变，且已验证不影响精度。

教训：任何参数或逻辑改动，必须在多场景上验证后才能作为默认；单场景提升可能是过拟合。

## 统计置信区间：之前多数结论不可判（2026-11-07）

对 7 个场景、每场景 300 帧的短遮挡事件做 bootstrap（5000 次重采样）：

```
合并恢复率 65/88 = 73.9%
95% 置信区间 [64.8%, 83.0%]，宽度 18.2 pp
```

**88 个事件不足以支撑 1–2 个百分点的差异判断。** 由此：

- 此前“新配置 71.5% vs 旧配置 75.3%”的差距完全落在噪声内；
- 单场景上的 ±0.5 pp 变化（如 04 的 89.5%→90.0%）是纯噪声；
- 参数调优的大部分时间可能都在追逐噪声。

要可靠判断 5 pp 级别的改进，事件量需达到 **300+**。

### LOSO（留一场景）验证

`base` 配置在 7 折中被全部选中（在其余场景平均最优），留出场景平均 75.0%，
与合并值一致，说明该配置是稳健选择而非恰好命中某一场景。

### 评测集扩展

为把事件量从 88 提到 300+，新增 `scripts/build_full_eval.py`，
将 7 个场景从 300 帧扩到完整序列（合计约 5300 帧），
使后续每项改动都能用 `scripts/loso_eval.py` 的置信区间来判断。

### 评估口径的隐藏问题

用 IoU≥0.5 匹配时，有 48.7% 的遮挡事件“一侧无匹配”被排除在统计外。
换用中心点距离（阈值 = 0.5×GT 框高）重算：

| 口径 | 成功 | 换 ID | 不可评估 |
|---|---|---|---|
| IoU 0.5 | 35.9% | 13.2% | 48.7% |
| 中心点 0.5×框高 | 43.2% | **38.0%** | 19.0% |
| 中心点 1.0×框高 | 46.6% | **44.6%** | 8.8% |

**IoU 口径把“框偏导致匹配不上”误计为“不可评估”，掩盖了真实的换 ID 比例。
实际换 ID 约 38–45%，而不是 13%。**

进一步拆分 73 个“重入后匹配不上”的事件：完全没检测到 26 个（36%）、
框偏差大 25 个（34%）、接近但不够 22 个（30%）——**64% 是检测到了但框对不上**。

### 尝试过但无效的改进

| 改动 | 结果 |
|---|---|
| 外观用近 15 帧中位数替代 EMA | 与 EMA 余弦相似度 0.9925，几乎等价，指标无变化 |
| 匹配区分度门限（margin） | 651 次匹配中仅拒绝 9 次；匹配 margin 中位数 0.861，本来就明确 |
| 离线轨迹拼接（外观 0.85 / 位置 0.05 / 间隔 90 帧） | 候选对为 0，一对都拼不上 |
| 离线轨迹拼接（放宽到 0.85/0.06/150） | 误合并 206，不可接受 |
| 放宽评估 IoU 到 0.4 / 0.3 | 恢复率反而下降到 85.4% / 81.6%，会引入错误匹配 |
| 框补全（被截断框用历史中位高度补齐） | 7 场景恢复率不变（0.739 vs 0.739）；单场景 04 上碎片 1.441→1.171、误合并 3→0、精确率 87.2%→89.6% |

### 框补全的定位

`correct_truncated_bbox`（默认关闭）针对“部分遮挡时检测框只覆盖可见部分”：
当当前框高小于历史中位高的 75% 时，保持底边、向上扩展到中位高度。

它改善了框质量与碎片指标，但**没有提升遮挡恢复率**——因为恢复判定取决于
断口前后 entity 是否一致，而框补全不改变 track 的身份连续性。

### 当前瓶颈判断

1. **检测侧**：约一半遮挡事件因“没检测到 / 框不准”而无法评估，
   而提高分辨率（2240）对低召回场景无效（13 场景 34.4%→35.1%）。
2. **关联侧**：逐帧匹配本身很果断（margin 大），换 ID 主要来自 track 真的断开后重建，
   不是匹配模糊；离线拼接受限于外观特征区分度，严了无效、松了误合并。

下一步若要继续提升，需要先解决“部分遮挡时检测框的完整性”，
或引入比外观更可靠的线索（体型、地面平面运动模型）。

### 事件量与置信区间的最终口径

将断口判定下限从 5 帧放宽到 2 帧（0.08 秒）后，全序列共得到 **319 个短遮挡事件**：

```
恢复率 76.5%（244/319）
95% 置信区间 [71.8%, 81.2%]，宽度 9.4 pp
```

该区间已收窄到可判断 10pp 级别改进的程度。`run_gate.py` 新增 `--min-gap` 参数，
默认仍为 5，需要更大样本时显式传 `--min-gap 2`。

### 分数归一化（z-norm）的实现与结果

在实体合并层新增 `use_score_norm`（默认关闭）：

```
best_z = (best_score - 候选分数均值) / 候选分数标准差
接受条件：best_z >= auto_merge_z（默认 0.8）
```

目的：把“跨场景固定的绝对阈值”换成“本帧候选内的相对优势”。

实测 7 场景 × 300 帧：**与基线完全相同（0.739 vs 0.739）**。
原因是候选分数的区分度本就很高，z 值普遍超过门槛，该条件几乎不改变决策——
与 margin 门限的结论一致：当前瓶颈不在“分数不够区分”，而在 track 断开后重建。
